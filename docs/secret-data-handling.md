# 秘密情報の取り扱いとメモリ管理：実装時の検討メモ

作成日：2026年11月26日  
対象：JWT、Cookie、APIキー、パスワード、暗号化用の鍵などを扱う実装

## 1. この文書の立場

秘密情報の管理に、あらゆるアプリへ適用できる唯一の正解があるとは考えない。守りたい情報、想定する脅威、言語仕様、実行環境、性能、使い勝手によって、適切な設計は変わる。

共通の検討方針は、**平文を扱う場所・時間・複製を、必要な範囲に抑えること**。ただし、参照を外すこと、メモリを上書きすること、保存済みデータを削除することは、それぞれ異なる操作として扱う。

「正解が一つではない」ことと、「仕様上保証される動作が曖昧でよい」ことは分ける。採用する方法について、何を保証でき、何を保証できないかを記録する。

この文書は設計・レビュー用の検討メモであり、記載した改善案をアプリへ実装したという報告ではない。

## 2. 最初に、何から守りたいかを決める

| 想定する問題 | 主に検討する対策 | その対策だけでは保証できないこと |
|---|---|---|
| 保存ファイルの持ち出し・誤共有 | 保存時の暗号化、鍵とデータの分離、ファイル権限 | 起動中に復号された値の保護 |
| 平文の長期保持・不要な複製 | 必要時の復号、保持期間の制限、受け渡し先の限定 | 利用中の平文を一切存在させないこと |
| ログ・画面・クリップボードへの漏出 | 出力内容の制限、マスク、表示終了時のクリア | すでに外部へコピーされた情報の回収 |
| 別アカウント・別テナントの取り違え | セッションと取得先の照合、保存領域と権限の分離 | 暗号化だけによるアカウント分離 |
| 実行中のプロセス自体の侵害 | 権限とプロセス境界の設計、秘密情報の受け渡し制限 | 保持時間の短縮だけによる侵害の解決 |

保存時の暗号化と、利用時のメモリ管理は、異なる問題に対する対策として検討する。

## 3. 取得・保存・破棄の窓口をまとめる

秘密情報を各所で直接読み出すより、管理サービスを通して扱う設計を検討する。復号、取得対象の照合、保持期間、ログへの出力方針を、一か所で確認しやすくするためである。

シングルトンは実現方法の一つ。起動時に管理オブジェクトを一つ作って必要な箇所へ渡す方法や、セッション単位で管理サービスを持つ方法も選択肢になる。

**管理オブジェクトの寿命と、平文の寿命は分けて設計する。** アプリ全体で使う管理サービスでも、平文まで起動中ずっと保持する必要があるとは限らない。

- 取得対象を、セッション・アカウント・接続先と結び付けて識別する。
- 呼び出し元へ、生の値を渡す必要があるかを確認する。管理側でコピーや送信まで行い、結果だけ返す方式も検討する。
- キャッシュする場合は、その理由、保持期間、失効条件を決める。
- 終了・例外・キャンセル・セッション削除の際、誰が何を手放すかを決める。
- サービス内で参照を削除しても、呼び出し元が保持する値までは消えないことを考慮する。

コールバック形式で「この処理の間だけ使う」と表現する方法もある。ただし、呼び出し元が値を別の変数へ保存したり、戻り値へ含めたりすれば保持は続く。APIの形だけで寿命を強制できるとは考えない。

## 4. 「クリア」「解放」「消去」を区別する

| 操作の例 | 期待できること | 注意点 |
|---|---|---|
| `token = null`、`token = ""` | その変数から以前の値を参照しなくなる | 元の文字列のメモリを上書きしたことにはならない |
| `map.delete(key)`、`map.clear()` | 管理用のMapから参照を取り除く | 他の変数・画面・非同期処理が保持する値は残り得る |
| ローカル変数のスコープを終える | 不要な参照が残らない構造にしやすい | クロージャや処理中のPromiseなどによる保持に注意する |
| 所有するBufferを `fill(0)` する | 対象Bufferの領域をゼロで上書きする | 別の文字列・コピー・別プロセスの領域まで消せるわけではない |
| 保存済みの項目を削除する | アプリから次回取得できる保存データを取り除く | メモリ内の値や、ディスク・バックアップ上の完全消去とは別の問題 |

JavaScriptの文字列は変更できない値であり、参照を手放した後の回収はGCに依存する。変数の代入やGCの実行を、元の内容の確実なゼロ消去として扱わない。[文字列の仕様に関する説明](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Data_structures#string_type)、[JavaScriptのメモリ管理](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Memory_management)

Node.jsの `Buffer.fill()` は対象領域を書き換える操作である。`Buffer` から文字列へ変換した後にBufferを上書きしても、その文字列の消去は保証しない。共有ビューがある場合は、同じ領域を使う処理への影響も確認する。[Node.jsのBuffer仕様](https://nodejs.org/api/buffer.html#buffillvalue-offset-end-encoding)

## 5. 言語・ランタイム・ライブラリの境界を確認する

JavaScriptでは、短いスコープ、長期キャッシュの回避、不要な参照の削除を中心に検討する。すべてのローカル変数へ機械的に `null` を代入するより、Map、イベントリスナー、クロージャ、画面状態など、参照を長く保持する場所を確認する。

明示的にメモリを扱える言語でも、解放・所有権の終了・デストラクタの実行が、秘密情報の上書きを自動的に保証するとは考えない。コピーや一時領域、コンパイラによる最適化も検討対象になる。たとえばlibsodiumは、通常の `memset()` 等による消去が最適化で除かれ得ることを説明し、専用の消去関数を提供している。[libsodiumのSecure memory](https://doc.libsodium.org/memory_management)

実装ごとに、次の境界をたどる。

1. OSやライブラリから、どの型で平文が返るか。
2. 文字列変換、JSON処理、ヘッダー生成などで、どこに値が複製されるか。
3. 非同期処理・再試行・キャンセルで、保持期間がどう変わるか。
4. どの領域を自分で上書きでき、どの領域は実行環境や外部ライブラリの管理になるか。

消去用の仕組みを導入する場合も、そのライブラリと対象プラットフォームでの保証範囲を確認する。今回のメモだけを根拠に、特定の言語や消去APIを万能な対策として採用しない。

## 6. 復号のタイミングとキャッシュは、条件に応じて選ぶ

| 方針 | 利点 | 判断が必要な点 |
|---|---|---|
| 必要になったときに復号する | アプリが平文を長期保持する場所を減らせる | 復号処理の回数、遅延、OS側の一時的な利用不可への対応 |
| 一定時間だけ保持する | 利用頻度と保持時間を調整できる | 期限、延長条件、失効時に残る利用中の参照 |
| 起動中保持する | 頻繁な利用を単純に実装しやすい | 長く保持する必要性、保持する件数、アプリ終了以外の破棄条件 |

「都度復号が常に正しい」「キャッシュが常に危険」と一律には決めない。利用頻度、必要な応答速度、扱う情報の重要度を踏まえて選ぶ。

保存形式も判断に関係する。全トークンを一つのJSONとして暗号化している場合、必要時に復号するだけでは、毎回全件が平文になる。必要な項目だけを復号したい場合は、暗号化・保存する単位の見直しも検討する。

画面を閉じて一時的な参照を手放す操作と、利用者が保存したトークンを削除する操作は分ける。メモリ保持を減らす変更によって、保存を選んだ情報まで意図せず失われないようにする。

## 7. Electronでは、管理するプロセスとOSの役割を分ける

このアプリで使う `safeStorage` は、暗号化・復号のAPIであり、KVSそのものではない。キーと値の対応、保存先、保持期間はアプリが管理する。

macOSではOSのキーチェーンを鍵の保管・取得に利用する。WindowsやLinuxでも同じAPI名を使えるが、鍵の保護方法や利用可否は環境で異なる。復号された文字列をアプリ側がどう保持するかは、引き続きアプリの設計事項である。[ElectronのsafeStorage仕様](https://www.electronjs.org/docs/latest/api/safe-storage)

管理窓口をメインプロセスへ置く場合は、次を検討する。

- シングルトンを作っても、プロセスをまたいで一つになるわけではない。別プロセスへの受け渡しで、平文のコピーが生じることを考慮する。
- 一覧表示には、必要に応じてマスクした値や期限等だけを返す。
- 全文表示のように平文を渡す必要がある機能では、要求元と取得対象を確認し、画面側の保持期間も設計する。
- 生のトークンを返す汎用APIを、閲覧中のWebページへ公開しない。

Electronは、特権操作を行うIPCについて送信元を検証するよう案内している。取得窓口を集約しても、呼び出せる相手の確認は別途必要になる。[ElectronのIPC送信元検証](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages)

## 8. UI・ログ・クリップボードも保持先として扱う

平文を保持するのは、管理サービス内の変数だけではない。入力欄、画面の状態、APIリクエストのヘッダー、エラー情報、ログも確認する。

全文表示を隠すだけでは、入力欄の値や画面の状態に残る場合がある。表示終了時に値をクリアする方針を検討する。ただし、それでもメモリの完全消去を保証するわけではない。

クリップボードへのコピーは、アプリの外へ値を渡す操作として扱う。一定時間後の自動クリアを採用する場合は、利用者が後からコピーした別の内容を消さないようにする。履歴機能等へ保存されたコピーまで回収できるとは扱わない。

ログや不具合調査用の出力は、秘密情報の値を含めずに原因を追える構成を検討する。実トークンを使って確認する代わりに、識別できる架空の値を使う。

## 9. 検証では、できることと証明できないことを分ける

通常終了に加えて、例外、タイムアウト、キャンセル、画面の終了、セッションの切り替えを確認する。管理用キャッシュや画面の値が残っていないか、別セッションの情報を返さないかを検証する。

保存時の暗号化については、専用の一時データと架空の値を使い、対象の保存ファイルに平文がないことと、再起動後に正常に復元できることを確認する。

Mapが空になったことや画面の値が消えたことは、アプリが参照を手放したことの確認になる。それだけで、メモリ全域から秘密情報が消えたと証明したことにはしない。メモリ使用量が下がったことも、秘密情報の消去の証明にはならない。

メモリダンプ等で調査する必要がある場合は、架空の値だけを使い、生成したダンプ自体も保持先として管理する。

## 10. 今回のMultisession Browserとの対応

2026年11月26日に確認した実装では、保存済みの手入力トークンを起動時に復号し、メインプロセスのMapで保持している。一時利用の手入力トークンも、別のMapで管理している。

管理オブジェクトは起動時に一つ作り、必要な箇所へ渡している。取得窓口の集約と、平文の保持期間の短縮は、別の設計課題になる。

コピー操作はメインプロセスからクリップボードへ書き込み、全文表示操作では管理用画面へ値を渡す。このため、保持期間を見直す際は、保存トークンのMapだけでなく、表示先・コピー先も検討対象になる。

今後の改善候補は、必要時の復号、保存単位の見直し、用途別の保持期間、画面側の参照の整理である。どこまで行うかは、業務上のリスク、使い勝手、変更の複雑さを踏まえて決める。

CookieはChromiumのCookie暗号化機能で扱うため、手入力トークン用の管理サービスと同じ実装ではない。また、ここで扱っている暗号化は、Local Storage等を含むプロファイル全体の暗号化を意味しない。

## 11. 設計判断を残すための記録項目

| 項目 | 記録する内容 |
|---|---|
| 対象 | どの情報を、どの機能で使うか |
| 想定する問題 | 保存ファイルの漏出、別セッションとの混同、平文の長期保持など |
| 採用方針 | 管理窓口、復号のタイミング、キャッシュの有無、保存単位 |
| 寿命 | 取得時点、利用終了の条件、例外時の処理、他へ渡した値の扱い |
| 保証範囲 | 参照の削除、特定Bufferの上書き、保存時の暗号化など、実際に保証できること |
| 残る制約 | 文字列の消去、外部ライブラリ内のコピー、OSや別プロセスの管理領域など |
| 検証 | 架空の値を使って確認したケースと、未確認の環境 |
| 見直す条件 | 他OSへの対応、共有・配布、扱う情報の重要度や利用頻度の変化など |
